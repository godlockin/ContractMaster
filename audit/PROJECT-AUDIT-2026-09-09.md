## 发现与修复建议

### F1 / P2：损坏 DOCX 中断整批处理

位置：`contract-review-cn/scripts/pipeline.py:131`、`:240–247`。

`ET.fromstring()` 遇到不完整 XML 抛出 `ET.ParseError`，不属于 prepare 捕获的异常集合。输入列表为损坏 DOCX + 有效 TXT 时，整个 prepare 退出，有效 TXT 未处理，candidate 未生成。与文档声明的“继续可处理文件、明确记录缺口”不一致。

复现：ZIP 中 `word/document.xml` 内容为 `<broken>`，后附正常合成 TXT；观察 `ParseError`，`valid_txt_processed=false`。

修复：在 DOCX 提取边界将解析错误转换为静态 `GateError`；按输入记录 gap 后继续。补坏 XML、损坏 ZIP 成员及合法后续输入组合测试。不要直接吞掉所有异常或把原始错误信息写入日志。

### F2 / P2：不可信文本作为活动 Markdown 输出

位置：`contract-review-cn/scripts/pipeline.py:432–448`。

证据引句、风险、建议等字符串直接拼接进 Markdown。合成合同中的 `![synthetic](https://example.invalid/audit-pixel)` 经合法引文校验后，原样进入最终报告。可允许外部图片的阅读器会将其解释为资源加载，而非合同原文；也能伪造标题和链接。

复现确认的是活动 Markdown 保留，未发送网络请求。是否实际联网取决于阅读器。不能将此描述为已证实任意文件泄露或通用 XSS。

修复：对不可信字段统一 Markdown 文本转义；证据用可靠的纯文本渲染方式；外链只在显式法源字段以校验后的 URL 输出。阅读器禁用远程图片作为纵深防护。人工复核 HTML 已做 HTML 转义，但不能直接拿 HTML 转义代替 Markdown 转义。

### F3 / P2：未验证的问题解决声明进入报告

位置：`contract-review-cn/scripts/pipeline.py:378`、`:439–445`；参照 `validate_depth.py:225–233`。

普通结果校验不检查 `question_resolutions`，报告却只凭匹配问题和 `status=resolved` 显示“声明已解决”，不再显示“待确认”。不传 `--depth` 时，缺少 reason 和 evidence_refs 的记录也可通过并渲染。报告整体仍标记 PARTIAL_AUDIT，但单项问题状态误导复核者。

复现：resolution 仅包含 question 与 status；生成报告出现“声明已解决”，证据为空。

修复：把 resolution 的结构、唯一性、问题关联及证据校验移入共享校验函数，所有 report 路径执行。未经证据验证的声明保持待确认；不要依赖可选深度校验补齐基本字段约束。

### F4 / P2：省略计划参数可漏验已激活专家

位置：`contract-review-cn/scripts/pipeline.py:328`、`:388–393`、`:488`。

run 已激活七角色计划后，调用 validate/report 时漏传 `--plan`，代码退回固定六角色；既不加载 active-plan，也不拒绝缺失计划。六份没有 plan_digest 的结果获得 VALIDATED_DECLARED_COVERAGE，第七名专家缺失未被发现。

复现：激活包含 security 的七角色计划，省略 plan 加载六份结果，accepted_roles=6。

边界：这不能绕过深度校验的 EXPERT_PLAN_NOT_VALIDATED 并取得完整深度状态；问题是计划约束在普通验证入口失效。

修复：已存在 active-plan 时强制提供匹配计划，或保存并自动加载计划快照；仅未激活过计划的历史 run 允许显式兼容模式。

### F5 / P2：交叉质询摘要没有绑定到具体 finding

位置：`research/public-contracts/tools/build_human_review.py:112–128`。

reviewed_report_sha256 仅映射 case_id；finding_id 也只检查是否属于该 case。同一合同有多批报告时，质询可以引用报告 A 的摘要，却裁定只出现在报告 B 的 finding，依然计入 cross_reviewed_findings。报告摘要防陈旧检查失去细粒度关联。

复现：A 包含 A1、B 包含 B1；质询填 A 的 SHA256 和 B1，构建成功并计数 1。

修复：维护 report_digest → case_id → finding_ids 的索引，要求目标 finding 实际存在于指定摘要文件。需要跨批引用时显式列出多个报告摘要。

### F6 / P2：全新克隆无法完整恢复公开语料

位置：`research/public-contracts/download_corpus.py:66–75`。

静态确认：仓库 manifest 的八项均标记 DOWNLOADED，下载器 todo 只包含历史 FAILED、新 ID 或硬编码 P05/P08，不检查本地原件、提取文本是否存在。README 说明第三方原件不随仓库发布，因此全新克隆仅尝试 P05/P08，其他六项继续沿用历史成功状态与旧绝对路径，复核包构建会因缺文件或路径越界失败。

本机恰好已有八份原件，不能靠本机现存文件验证新克隆流程。未联网重下载；结论来自筛选条件、manifest 元数据及发布说明。

修复：区分历史来源记录和本地材料就绪状态；逐项检查本地文件存在性与 hash。缺原件则下载，缺派生文件则重建；使用语料根目录相对路径。增加仅保留仓库跟踪文件的恢复测试，并注入离线下载器。

### O1：脱敏重叠匹配达到平方级耗时

位置：`contract-review-cn/scripts/pipeline.py:187–190`。

每个候选匹配扫描全部 selected，即使完全不重叠也如此。使用重复合成手机号测量，结果如下；时间是本机单轮样本，不是生产容量结论。

| 匹配数 | 耗时 |
|---|---:|
| 2,000 | 0.0371 秒 |
| 4,000 | 0.1475 秒 |
| 8,000 | 0.5845 秒 |

输入增加 4 倍，耗时增加 15.75 倍，与 O(M²) 代码路径一致。

修复：保留最长优先、相同长度按位置、显式词典优先等现有语义，采用可查询重叠的区间索引或坐标压缩结构。不要只改成按起点贪心，那会改变重叠实体脱敏结果。先加入小输入差分验证，再比较典型长文档耗时。

## 其他改进方向

1. **校验契约集中化**：JSON 目前依赖松散 dict 与分散字段检查。共享结果/问题解决/法源引用 schema；区分类型错误、未完成状态、IO 错误。采用 TypedDict 或数据模型支持静态检查。
2. **产物原子提交**：prepare/release 多步写入失败后留下中间目录；报告固定 write_new，补审后无法在同一目录再次生成。用临时目录提交及版本化报告，让重试保留历史且可完成。
3. **默认离线 CI + 可选 PDF CI**：当前可选依赖缺失会跳过 PDF 测试。建立标准库核心测试与安装 pypdf 的独立矩阵，显式记录解析库版本，加入本报告的边界用例。
4. **人工复核可恢复**：页面仅内存保留且无导入，文档已提示刷新会丢失。可增加导出 JSON 的导入恢复，并验证 package_manifest；持久化策略需保持隐私边界。
5. **法律质量独立评测**：开发集命中率不能替代律师裁定。加入独立专家标签、误报率、严重程度校准、负例和跨文档漏检统计。项目已明确不报告法律准确率，此处属于下一阶段建设。

## 建议顺序

第一批修 F2 输出转义及 F3/F4/F5 校验关联；第二批修 F1 输入容错、F6 新克隆恢复；第三批改进产物重试与 CI，再按真实文档规模推进 O1。

本次只新增审查报告及复现脚本，未修改业务源码。现有隐私确认、原文摘要、映射摘要、权限和证据偏移校验值得保留；声明型验证无法证明模型实际完成认知审核，项目已明确这一边界，不将它重复计为程序漏洞。
