第二轮确认 5 项边界缺陷与 1 项性能瓶颈。未修改业务代码；新增 `recheck_boundaries.py`，仅使用临时合成输入、离线故障注入。脚本成功表示发现仍存在，不代表已经修复。

## B1 / P2：下载失败丢失历史摘要，下次重试不再核验

位置：`research/public-contracts/download_corpus.py` 的 `fetch` 异常返回、`main` 中 expected_sha256 传入和 manifest 覆盖。

fetch 失败只返回本次来源元数据和 FAILED，不保留之前 sha256。main 用失败记录覆盖历史成功记录。下一次运行从新 manifest 取 sha256，得到 None；即使第一次失败是摘要不匹配，第二次也不再要求匹配原版本。

合成复现：初始摘要 PINNED，连续两次注入与真实异常返回相同形状的离线失败；捕获校验参数依次为 PINNED、None。未下载或更改真实语料。

建议：将不可变来源基准与每次下载尝试状态分开保存；失败不能删除原摘要。摘要不符必须持续失败，直至显式版本更新。补连续失败与失败后恢复测试。

## B2 / P2：全部下载失败，命令仍正常结束

位置：同文件 `main` 末尾及 `if __name__ == '__main__'`。

fetch 把异常转换为 FAILED 数据，main 写清单、打印结果后正常返回，CLI 无非零退出码。自动化只检查返回值时，会把缺少 pypdf、网络失败或完整性失败判为任务成功。

合成复现：所有注入下载均 FAILED，main 仍正常返回；CLI 入口没有额外失败状态处理。这与 B1 是两个独立问题：一个破坏持久化基准，一个误报执行状态。

建议：保留逐项结果，任一请求项失败则返回非零；明确区分全部成功、部分失败、全部失败。

## B3 / P2：提取文本和原件摘要读取不在同一快照

位置：`contract-review-cn/scripts/pipeline.py` 的 prepare：先 extract(path)，处理完成后再次 path.read_bytes() 计算摘要；实体词典也在加载后再次读取摘要。

当编辑器在两次读取之间保存文件，candidate 可以保存旧文本，extraction.json 却绑定新文件摘要。release 与新文件比较后通过。不是摘要算法失效，而是摘要计算对象与被审核内容不同。

合成复现：提取付款 100 元版本后、计算摘要前，模拟外部编辑器保存 200 元版本；release 成功，公共包仍为 100 元，当前源文件为 200 元。

建议：读取一次不可变字节快照，提取和摘要均来自快照。DOCX/PDF 用内存流或私有快照文件；词典同样处理。用户复核只能补充质量确认，不能替代版本绑定。

## B4 / P2：无效“已核实”法源仍获得完整深度状态

位置：`pipeline.py` 的 finding.basis 校验；`validate_depth.py` 的 findings 循环。

finding 的 verified 依据只要求非空日期及以 https:// 开头的字符串，没有验证主机、日期格式，也没有与 depth.sources 关联。depth.sources 自身有较严格校验，但 finding.basis 的资料未必属于该目录。

合成复现：六角色结果通过普通校验，某 finding 填 `url="https://"`、`checked_at="not-a-date"`、与法源目录不相干的标题，深度结果仍为 DECLARED_DEPTH_COMPLETE。

这是可机器校验的结构与关联缺口，不是要求程序证明法律结论真实。

建议：共享 URL/日期验证；finding.basis 引用 source_id 和具体条文，禁止用另一份合法目录替代实际引用的核验状态。保持“结构通过不证明法律正确”的边界。

## B5 / P2：发布与审计写入不原子，失败后状态难恢复

位置：`pipeline.py` release：先创建 public/bundle.json，再 append RELEASED 审计事件。

审计写入失败时，调用返回错误，但公共包已经存在；后续重试先遇到 ALREADY_RELEASED，无法正常补齐事件。也没有单独的完成标记区分已提交与中途失败。

合成复现：将临时 run 的审计日志位置替换为目录以注入写入错误；release 抛 IsADirectoryError，但 public/bundle.json 已生成；恢复日志位置后重试仍拒绝。

建议：定义发布状态机与提交点；暂存公共包、记录可恢复状态，再原子提交。重试可校验摘要后补齐未完成步骤。实际发布仍需已有人工复核授权。此问题不绕过人工 attest，也未证明未经复核数据被发送到外部。

## O2：分段在边界对齐的长文本中重复扫描后缀

位置：`pipeline.py` segments_for 中对 remaining 执行 TOKEN.finditer 的循环。

若 3000 字符边界未切入任何 token，循环会继续扫描整个剩余文本；下一段再扫描一次。字符串后缀复制也增加开销。上一轮优化的是 redact 的重叠查询，没有改变该路径。

合成测试使用无换行的 12 字符单元 `⟦ORG_0001⟧` 加两个空格，使边界恰好对齐：

| 单元数 | 耗时 |
|---|---:|
| 10,000 | 0.0229 秒 |
| 20,000 | 0.0897 秒 |
| 40,000 | 0.3524 秒 |

数据量增加 4 倍，耗时约 15.4 倍。这是特定输入路径的本机样本，不代表所有合同都慢。边界切入 token 的对照样本没有同样增长。

建议：当 match.start() >= end 时立即停止扫描；进一步用原字符串索引或一次 token 遍历替代反复切后缀。继续验证 token 不截断、字符往返和 offset 正确。
